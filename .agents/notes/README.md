# Agent Notes

本目录存放一类设计文档。**Agent Note** 记录影响本代码库的决策或提案：代码和测试无法
承载的*为什么*、放弃了什么、以及什么验证兜底。本文件是机制权威，规定存放位置、
何时需要写、文件格式、生命周期与归档规则。

> **与发行文档的分工**：[`docs/releases/`](../../docs/releases/) 面向用户描述"这个版本
> 发了什么"；Agent Note 面向维护者记录"当时为什么这样决定、否决了什么"。二者互补，
> 互不替代。

本机制移植自 DeepSeek Harness（dsh）的 Agent Notes，按本仓库情况做了简化适配
（见 [与 dsh 的差异](#与-dsh-的差异)）。**正文一律中文，单文件制**：没有 `.zh.md`
对侧文件，也没有 i18n 伴随记录。

## 布局与命名

每份 Agent Note 有两个维度，都编码在其**路径**中：`{lifecycle}/{class}/yyyy-mm-dd-topic.md`。

- **生命周期**（顶层文件夹）是 Note 的状态，随状态变化在文件夹之间移动：
  - **`proposed/`**：实施前评审的提案；尚未构建（或仅部分构建）。
  - **`implemented/`**：决策已交付，**与实际交付内容保持同步**：代码后续移动文件、
    改名、换默认值时，Note 在同一个变更里同步更正（只改事实——路径、名称、结构——
    不改决策本身）。见 [implemented/AGENTS.md](implemented/AGENTS.md)。
  - **`rejected/`**：提案讨论后被否决。仅当其决策依据仍能避免一种诱人且影响重大的
    错误时保留；否则整文件删除。
  - **`archived/`**：已实施记录中历史价值大于指导价值的部分，封存后冻结，见
    [归档与删除](#归档与删除)。
- **类别**（次级文件夹）是决策的*种类*，见下方[分类](#分类)。

文件名中的日期是该主题**首次提出**的时间（以 git 历史为准）；slug 用 ASCII 小写
连字符（便于 grep 与链接）。Note 之间的交叉引用一律使用相对 Markdown 链接
（`[主题](../../implemented/architecture/2026-…-….md)`），不使用纯文字编号——
这样可被[门禁](#门禁)机械校验，且在文件夹间移动时仍有效。

活跃目录树就是工作清单：浏览生命周期/类别文件夹，或全仓库搜索。**不要添加
`INDEX.md`**（门禁直接拒绝）：它重复路径元数据，还会让无关变更争用同一个文件。

## 分类

每份 Note 属于下表封闭集合中的一个类别；类别改动需同时更新本表与
[`scripts/verify-agent-notes.mjs`](../../scripts/verify-agent-notes.mjs) 的 `CLASSES`。

| 类别 | 覆盖范围 |
|---|---|
| `feature` | 面向用户的新能力。 |
| `bug-fix` | 修正缺陷或弥补验证发现的缺口。 |
| `simplification` | 不增加能力的前提下移除代码、行为或对外范围。 |
| `architecture` | 关于**交付源码**的结构性决策：模块关系、数据流、运行时词汇。 |
| `process` | 代码**周边**的工具、策略或工作流——门禁、发行、依赖选型——不涉及运行时行为。 |
| `testing` | 测试基础设施与策略（本仓库即 `npm run verify` 断言体系）。 |

`architecture` 与 `process` 的界线：**architecture** 关乎交付的源码；**process**
关乎围绕源码的工具与工作流。（不设 `refactor`：它与 `simplification` 重叠，而后者
的判别标准「可观察行为是否改变」已经覆盖它。）

## 何时需要写一份

**每个非平凡变更**，在同一 PR 内新增或更新至少一份 Agent Note。非平凡变更包括：
行为、结构与跨文件契约、流程或工具、测试策略、磁盘/协议/配置格式，以及维护者可能
重新审视的其他决策。

- 更新**已经拥有该决策**的 Note 即满足规则；没有归属时才新写一份，不造重复记录。
- **豁免**：纯机械或局部编辑，包括局部 UI 展示与交互调整。
- 对未来重大工作的提案从 `proposed/` 开始；已经做出的决策直接进 `implemented/`。
- Note **永不被改成另一个决策**：用新 Note 取代旧的并互相链接。被完全取代的
  implemented Note 可合并进当前持有者后删除，前提是保留其全部独有的依据、替代方案、
  影响与验证，并修复所有入站链接；仅部分取代的保留双方并互相链接。
- 「平凡与否」由 review 判断，**不设自动分类门禁**——机械检查无法可靠判断语义上的
  重大程度。

## 谁写，以及合入权在哪

**责任落在变更，不落在人**：非平凡变更须有 Note，由说得出理由的人撰写。
本仓库只有一位维护者，故由维护者撰写；需要时用 `npm run note -- <class> <slug>`
生成合规骨架（脚手架只摆骨架，**不判断变更是否非平凡**，那是 review 的事）。

- **本仓库不接受外部 PR**（见 [CONTRIBUTING.md](../../.github/CONTRIBUTING.md)），
  因此不为外部贡献者设计 Note 撰写权或准入规则。**权限属于 PR 准入轨道，不属于
  决策记录**：全文件格式不含作者字段，署名以 git 历史为准，不设 `Author:` 行。
  （上游 dsh 同此设计：455 份 implemented Note 皆无署名，权限由其
  `review-ownership/approval-policy.json` 单独承担。）
- 该姿态带**回退条件**，写在
  [PR 模板与贡献准入策略](implemented/process/2026-10-04-pr-template-and-contribution-policy.md)：
  出现持续高质量的外部贡献者，或决定引入 i18n / 第二位维护者时重新评估。

## 文件格式

格式由 `npm run verify:notes`（[`scripts/verify-agent-notes.mjs`](../../scripts/verify-agent-notes.mjs)，
CI 同步执行）强制。**机器检查的 token 保持英文**（`# Agent Note: `、`Status:`、
`Archived:`），**规范章节名固定为中文**且逐字如下。

### 头部块

每份 Note 的前几行严格为：

```markdown
# Agent Note: <标题>

Status: <状态>
```

后跟空行。`Status:` 与文件夹交叉校验：

- `proposed/` → `Status: proposed`
- `implemented/` → `Status: implemented`
- `rejected/` → `Status: rejected — <一行原因>`（唯一带内容的状态：读者查被否决的
  Note 时，结论正是他要找的）
- `archived/` → `Status: implemented`，其下**紧跟一行** `Archived: YYYY-MM-DD`

状态行不带日期、不带括号补充：文件名记录首次提出日期，git 记录其余一切。

### 正文骨架

正文以 `## 问题` 开篇——动机，写法上不依赖解决方案即可独立成文。固定章节用下列
规范名称（门禁逐字校验），真正独特的技术细节可在必需章节之间自由组织。

#### `proposed/`

```markdown
## 问题
## 提案
……自定义章节……
## 曾考虑的替代方案
## 验收标准
## 风险
```

`## 提案` 可以合理地使用将来时态——计划、迁移步骤、待解决问题在工作未完成时属于
此处。`## 验收标准` 说明什么可观察状态意味着完成。`## 风险` 涵盖可能出错的事项与
本变更有意放弃的东西。

#### `implemented/`

```markdown
## 问题
## 决策
……自定义章节……
## 曾考虑的替代方案
## 后果
```

`## 决策` 以现在时态描述已交付的现实。`## 后果` 记录权衡的代价**与**收益。
提案期章节名在此属于规格用语，门禁拒绝：`## 提案`、`## 计划`、`## 迁移计划`、
`## 验收标准` 不得出现（须折入 决策/后果）。`## 测试`、`## 相关` 等陈述现在时
事实的自定义章节是允许的。

#### `rejected/`

被否决的 Note 是冻结的提案：保留提案时的所有章节，结论写在 `Status:` 行上。
只要求 头部块、`## 问题` 开篇、`## 提案`、`## 曾考虑的替代方案`。

### 曾考虑的替代方案——必需，无豁免

每份 Note 都必须有 `## 曾考虑的替代方案`：每个真实替代方案及其落选原因，一个
加粗引导的段落，或对争议较大的用 `### 为何不 <X>?` 子节。记录决策时不记录它击败
了什么，就是在邀请反复争论——这正是 Agent Note 要防止的问题。**替代方案是记录下来
的，不是凭空编造的**；本仓库没有历史存量，不设任何豁免注释。

### 在生命周期之间移动

移动文件夹意味着在同一个变更里改 `Status:` 行并重写骨架，否则门禁失败：
`proposed/` → `implemented/` 把 `## 提案` 改写为现在时的 `## 决策`，将
`## 验收标准` 与 `## 风险` 折入 `## 后果`，用实际交付内容替换计划；
`proposed/` → `rejected/` 仅在 `Status:` 行补上原因并冻结。

## 归档与删除

- 仅描述小型 UI 调整或纯机械变更的 implemented Note **直接删除**，并修复或移除
  入站链接。局部 bug 修复、性能变更、新能力、实质行为决策**不会**仅因实现小而符合
  删除条件。
- 其他已实施记录，只有在决策完整落地、依据不太可能再指导未来工作、但仍具历史决策
  价值时，移入 `archived/{class}/yyyy-mm-dd-topic.md`（有意省略 `implemented`：
  只有已实施记录能进归档）。归档变更只允许：移动文件、在 `Status:` 行下插入
  `Archived:` 行、修复或删除入站链接。
- **`archived/` 一经封存即永久冻结**：不编辑、不移动、不删除，也不作为当前行为的
  权威依据；活跃文档仍可链接进归档记录历史。当前门禁校验其结构与 `Archived:` 行，
  内容哈希封存等更强约束留待后续门禁调整时加入。
- **绝不归档 `proposed/`**：过时的提案转 `rejected/`。`rejected/` 仅当仍能避免
  可能发生的错误时保留，否则整文件删除。

## 门禁

```bash
npm run verify:notes
```

零依赖 Node 脚本，CI 三平台执行，发行流水线（`release.yml` 复用 CI）同步生效。
检查项：

1. **目录树**：生命周期与类别封闭集合、层级深度、文件名格式、禁止 `INDEX.md`；
2. **头部**：`# Agent Note: ` / 空行 / `Status:` 语法，状态与文件夹一致，状态行全文唯一；
3. **骨架**：首章节为 `## 问题`、各生命周期必备章节、implemented/archived 禁用提案期章节名；
4. **替代方案**：`## 曾考虑的替代方案` 必备；
5. **链接**：活跃文档的相对链接可解析（`archived/` 按冻结规则不查出站链接）。

## 与 dsh 的差异

| 方面 | dsh | 本仓库 |
|---|---|---|
| 语言 | 英文 + `.zh.md` 对侧 + `.i18n.yaml` 伴随记录 | 仅中文，单文件 |
| 规范章节名 | 中英各自一套，配对门禁查一致性 | 固定中文一套（机器 token 仍为英文） |
| 格式豁免 | grandfather 注释（历史存量） | 无豁免（无历史存量） |
| 归档封存 | manifest + 内容哈希，独立校验脚本 | 冻结靠约定 + 结构/`Archived:` 门禁，哈希封存留待后续 |
| 门禁接入 | `pnpm doc-sync` + lefthook + 多脚本 | 单一零依赖脚本 + GitHub Actions |
